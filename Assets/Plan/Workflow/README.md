# TFT Data Analyzer Master Workflow

작성일: 2026-09-23
갱신일: 2026-10-19
상태: 활성 워크플로우 규칙

## 1. 목적

이 문서는 TFT Data Analyzer의 모든 변경을 `기획 → 개발 → QA → 문서` 순서로 운영하기 위한 총괄 규칙이다. Master AI는 단계 전환, 역할 분리, 승인 상태, 기록, 체크포인트를 관리한다.

각 작업은 하나의 사이클로 관리한다. 현재 사이클의 기획이 승인되기 전에는 제품 코드 개발을 시작하지 않는다.

## 2. 역할과 모델 선택 기준

모델·추론 수준은 루트 [AGENTS.md](../../../AGENTS.md)의 작업 수준 기준을 따른다. 판단이 애매하면 [상세 지침](../../../docs/agent-model-policy.md)을 참고하고 실제 배정과 변경 이유를 기록한다. 2026-10-19 사용자 확정에 따라 기획 A는 Antigravity, 기획 B는 GPT가 맡는다. 각 환경 안의 구체적인 모델·추론은 작업 수준 기준으로 선택하고 실제 실행값을 기록한다.

| 역할 | 책임 |
|---|---|
| Master AI | 범위·승인·단계 전환·통합 판단 |
| 기획 A — Antigravity | 제품 범위, 정책, 사용자 가치, 승인 범위, 위험 검토 |
| 기획 B — GPT | 기술 구조, 테스트 가능성, 예외·복구, 완료 조건 검토 |
| 개발 리드 | 승인 기획 인수, 작업·검수 에이전트 조율 |
| 구현 에이전트 | TDD 기반 코드 작성과 검증 |
| 개발 검수 에이전트 | 읽기 전용 코드·테스트·범위 검수 |
| QA 에이전트 | TODO 대비 결과, 예외, 회귀, 증거 검증 |
| 문서 에이전트 | 승인된 결과를 사용자용 문서로 정리 |

## 3. 단계별 계약

### 3.1 기획

1. Master AI가 작업 범위와 현재 저장소 상태를 고정한다.
2. 기획 A(Antigravity)와 기획 B(GPT)가 동일한 기준 커밋·입력 snapshot을 바탕으로 서로의 초안을 보지 않고 읽기 전용 검토한다. Antigravity 요청·응답은 [협업 폴더](../../../AntigravityCollab/README.md)에 기록하며, 연결 실패를 GPT의 대행 검수로 조용히 대체하지 않는다.
3. Master AI가 공통 결론, 충돌 의견, 권고안을 통합한다.
4. 개발 TODO마다 객관적인 완료 조건, 검수 조건, QA 증거를 연결한다.
5. 정제 기획안과 raw 요청·응답을 Markdown으로 저장한다.
6. 사용자의 명시적 승인을 기다린다.

기획 승인은 해당 문서에 적힌 범위만 승인한다. 네트워크 수집, 외부 배포, 다음 Phase 등 문서 밖의 작업 권한으로 확대하지 않는다.

#### 기획 검수 필수 점검 기준 ([Antigravity 기획 검수안](../../../AntigravityCollab/2026-10-19-project-plan-review.md) 반영)

기획 A(범위·정책·사용자 가치)와 기획 B(기술·검증·완료 조건)는 독립 검토 시 다음 네 가지를 필수로 확인한다.

- **Fail-Closed 정책의 실데이터 통과 경로**: 최소 표본(`n >= 100`)이나 증강 정책 분류(`MetricPolicyMetadata`) 같은 안전 차단 규칙을 둘 때, 정상적인 기준 카탈로그·실데이터가 영구 차단되지 않도록 검토된 메타데이터 공급 경로(또는 명시적 미공급 한계 고지)가 함께 정의되어 있는지 확인한다.
- **집계 입도와 최소 표본의 달성 가능성**: 수집 상한(예: 실행당 1,000경기) 대비 조합 지문(`CompositionFingerprint`)이나 필터의 입도가 지나치게 세분화되어 실제 분석에서 비율 지표가 모두 `표본 부족`으로 억제되는지 점검하고, 현재 범위의 한계 고지 또는 별도 집계 입도 개선 범위를 구분한다.
- **백그라운드·시작 작업의 비차단·창 무결성·경로 보안**: `[InitializeOnLoad]`나 지연 작업이 모달 팝업·새 EditorWindow를 띄워 창 잔류를 유발하지 않는지, 비교 기준 버전(예: `CatalogIndex` 대 로컬 상태 파일)이 명확한지, `Library/TftAnalyzerStore` 하위 상태 파일에 `RejectReparsePoints`와 손상 시 비차단 처리가 적용되는지 확인한다.
- **상위 설계 대비 하위 확정 계약의 일관성**: HTTP 429 즉시 중단·수동 재시도 UTC 표시, Player 빌드 전용 차단(개인 연구용 Editor 및 로컬 CSV 허용)처럼 보안·사용성을 위해 하위 계획에서 구체화한 계약을 상위 설계 문구와 혼동해 회귀시키지 않는다.

### 3.2 개발

1. 기획 승인 후 Master AI가 개발 리드에게 승인 문서와 TODO를 전달한다.
2. 개발 리드는 구현 에이전트와 읽기 전용 검수 에이전트를 만든다.
3. 구현 에이전트는 TODO 단위로 실패 테스트 → 최소 구현 → 통과 테스트 순서를 따른다.
4. 검수 에이전트는 코드를 변경하지 않고 요구사항, 회귀 위험, 테스트 증거를 검토한다.
5. 검수에서 반려되면 같은 TODO를 구현 에이전트에게 되돌린다.
6. 모든 TODO가 검수 승인될 때만 QA로 이동한다.

### 3.3 QA

1. QA 에이전트는 승인된 TODO와 실제 diff·테스트·산출물을 대조한다.
2. 미구현, 과구현, 예외, 데이터 손상 위험, 불충분한 테스트를 기록한다.
3. 실패나 기획 모호성이 있으면 해당 내용을 기획 에이전트들에게 되돌린다.
4. 기획 변경이 필요하면 개발로 바로 돌아가지 않고 기획 승인부터 다시 시작한다.
5. 모든 필수 증거가 확인될 때만 문서 단계로 이동한다.

### 3.4 문서

1. 정제 문서는 사용자 관점의 목적, 결정, 변경, 사용법, 제한, 검증 결과를 담는다.
2. raw 문서는 에이전트에게 전달된 실제 프롬프트와 Master AI가 받은 공개 가능한 응답을 담는다.
3. 숨겨진 내부 추론, 비밀값, API 키, 개인정보는 raw 문서에도 기록하지 않는다.
4. 문서와 실제 코드 상태가 일치하는지 마지막으로 확인한다.
5. 사용자가 최종 결과를 승인해야 사이클을 완료 처리한다.

## 4. 기록 구조

```text
Assets/Plan/Workflow/
  README.md
  Cycles/
    YYYY-MM-DD-<cycle-name>/
      refined/
        PlanningReview.md
        ImplementationPlan.md
        DevelopmentReport.md
        QAReport.md
        FinalDocumentation.md
      raw/
        MasterCoordination.md
        PlanningAgentA.md
        PlanningAgentB.md
        DevelopmentLead.md
        Implementer.md
        Reviewer.md
        QAAgent.md
        DocumentationAgent.md
      Checkpoint.md
```

존재하지 않는 단계의 파일은 미리 성공한 것처럼 만들지 않는다. 단계가 시작되면 생성하고, 실행하지 않은 검증은 `미실행`으로 기록한다.

실행 순서, 개발 TODO, 완료·검수 조건, QA 증거와 체크 상태는 `refined/ImplementationPlan.md` 한곳에서 관리한다. 기존 `DevelopmentTodo.md`는 통합 문서를 가리키는 안내 파일로만 유지한다.

현재 재개 위치는 `Checkpoint.md`, 당시 구현·검증 결과는 날짜가 명시된 `DevelopmentReport.md`와 `raw/`에서 확인한다. 과거 보고서와 raw 기록은 이력 보관용이며, 당시 프롬프트·모델 배정·환경 오류를 새 작업 지침이나 현재 실행 결과로 적용하지 않는다. 기존 참조를 보존하기 위해 기록을 이동하거나 중복 복사하지 않는다.

## 5. 승인 상태

각 정제 문서는 다음 상태 중 하나를 명시한다.

- `초안`
- `승인 대기`
- `승인됨`
- `반려됨`
- `진행 중`
- `검증 실패`
- `완료`

기획 승인과 최종 완료 승인은 사용자가 명시적으로 내린다. 개발 검수와 QA 통과는 담당 에이전트의 증거 기반 승인 후 Master AI가 단계 전환을 확정한다.

## 6. 체크포인트 규칙

다음 상황마다 `Checkpoint.md`를 갱신한다.

- 단계가 전환될 때
- 사용자 승인을 기다릴 때
- 테스트 또는 외부 상태로 작업이 중단될 때
- 컨텍스트나 토큰 부족이 예상될 때
- 예외가 기획 단계로 되돌아갈 때

체크포인트에는 최소한 다음을 기록한다.

- 현재 사이클과 단계
- 승인된 범위와 미승인 범위
- Git HEAD와 작업 트리 상태
- 완료·미완료 TODO
- 마지막 검증 명령과 결과
- 변경하면 안 되는 사용자 파일
- 재개 시 첫 행동

## 7. 완료 정의

다음 조건을 모두 만족해야 한 사이클을 완료로 판단한다.

1. 승인된 기획과 TODO가 존재한다.
2. 모든 개발 TODO가 구현 및 읽기 전용 검수를 통과했다.
3. QA가 TODO, 예외, 회귀, 산출물 증거를 통과시켰다.
4. 정제 문서와 raw 기록이 저장됐다.
5. 체크포인트가 최종 상태를 가리킨다.
6. 사용자가 최종 결과를 승인했다.
