# TFT Data Analyzer Master Workflow

작성일: 2026-09-23
상태: 활성 워크플로우 규칙

## 1. 목적

이 문서는 TFT Data Analyzer의 모든 변경을 `기획 → 개발 → QA → 문서` 순서로 운영하기 위한 총괄 규칙이다. Master AI는 단계 전환, 역할 분리, 승인 상태, 기록, 체크포인트를 관리한다.

각 작업은 하나의 사이클로 관리한다. 현재 사이클의 기획이 승인되기 전에는 제품 코드 개발을 시작하지 않는다.

## 2. 역할과 기본 모델 배정

모델은 작업 난이도와 현재 사용 가능한 모델에 따라 Master AI가 조정할 수 있다. 조정 시 해당 사이클 기록에 이유를 남긴다.

| 역할 | 기본 모델 | 책임 |
|---|---|---|
| Master AI | 현재 루트 세션 모델 | 범위·승인·단계 전환·통합 판단 |
| 기획 A | `gpt-6-astra`, high | 제품 범위, 정책, 사용자 승인, 위험 검토 |
| 기획 B | `gpt-6-sol`, high | 기술 구조, 테스트 가능성, 완료 조건 검토 |
| 개발 리드 | `gpt-6-astra`, high | 승인 기획 인수, 작업·검수 에이전트 조율 |
| 구현 에이전트 | `gpt-6-sol`, xhigh | TDD 기반 코드 작성과 검증 |
| 개발 검수 에이전트 | `gpt-6-astra`, high | 읽기 전용 코드·테스트·범위 검수 |
| QA 에이전트 | `gpt-6-astra`, high | TODO 대비 결과, 예외, 회귀, 증거 검증 |
| 문서 에이전트 | `gpt-6-sol`, medium | 승인된 결과를 사용자용 문서로 정리 |

## 3. 단계별 계약

### 3.1 기획

1. Master AI가 작업 범위와 현재 저장소 상태를 고정한다.
2. 기획 에이전트 2명이 서로 독립적으로 현재 기획을 읽기 전용 검토한다.
3. Master AI가 공통 결론, 충돌 의견, 권고안을 통합한다.
4. 개발 TODO마다 객관적인 완료 조건, 검수 조건, QA 증거를 연결한다.
5. 정제 기획안과 raw 요청·응답을 Markdown으로 저장한다.
6. 사용자의 명시적 승인을 기다린다.

기획 승인은 해당 문서에 적힌 범위만 승인한다. 네트워크 수집, 외부 배포, 다음 Phase 등 문서 밖의 작업 권한으로 확대하지 않는다.

### 3.2 개발

1. 기획 승인 후 Master AI가 개발 리드에게 승인 문서와 TODO를 전달한다.
2. 개발 리드는 구현 에이전트와 읽기 전용 검수 에이전트를 만든다.
3. 구현 에이전트는 TODO 단위로 실패 테스트 → 최소 구현 → 통과 테스트 순서를 따른다.
4. 검수 에이전트는 코드를 변경하지 않고 요구사항, 회귀 위험, 테스트 증거를 검토한다.
5. 검수에서 반려되면 같은 TODO를 구현 에이전트에게 되돌린다.
6. 모든 TODO가 검수 승인될 때만 QA로 이동한다.

### 3.3 QA

1. QA 에이전트는 승인된 TODO와 실제 diff·테스트·산출물을 대조한다.
2. 미구현, 과구현, 예외, 데이터 손상 위험, 불충분한 테스트를 기록한다.
3. 실패나 기획 모호성이 있으면 해당 내용을 기획 에이전트들에게 되돌린다.
4. 기획 변경이 필요하면 개발로 바로 돌아가지 않고 기획 승인부터 다시 시작한다.
5. 모든 필수 증거가 확인될 때만 문서 단계로 이동한다.

### 3.4 문서

1. 정제 문서는 사용자 관점의 목적, 결정, 변경, 사용법, 제한, 검증 결과를 담는다.
2. raw 문서는 에이전트에게 전달된 실제 프롬프트와 Master AI가 받은 공개 가능한 응답을 담는다.
3. 숨겨진 내부 추론, 비밀값, API 키, 개인정보는 raw 문서에도 기록하지 않는다.
4. 문서와 실제 코드 상태가 일치하는지 마지막으로 확인한다.
5. 사용자가 최종 결과를 승인해야 사이클을 완료 처리한다.

## 4. 기록 구조

```text
Assets/Plan/Workflow/
  README.md
  Cycles/
    YYYY-MM-DD-<cycle-name>/
      refined/
        PlanningReview.md
        DevelopmentTodo.md
        DevelopmentReport.md
        QAReport.md
        FinalDocumentation.md
      raw/
        MasterCoordination.md
        PlanningAgentA.md
        PlanningAgentB.md
        DevelopmentLead.md
        Implementer.md
        Reviewer.md
        QAAgent.md
        DocumentationAgent.md
      Checkpoint.md
```

존재하지 않는 단계의 파일은 미리 성공한 것처럼 만들지 않는다. 단계가 시작되면 생성하고, 실행하지 않은 검증은 `미실행`으로 기록한다.

## 5. 승인 상태

각 정제 문서는 다음 상태 중 하나를 명시한다.

- `초안`
- `승인 대기`
- `승인됨`
- `반려됨`
- `진행 중`
- `검증 실패`
- `완료`

기획 승인과 최종 완료 승인은 사용자가 명시적으로 내린다. 개발 검수와 QA 통과는 담당 에이전트의 증거 기반 승인 후 Master AI가 단계 전환을 확정한다.

## 6. 체크포인트 규칙

다음 상황마다 `Checkpoint.md`를 갱신한다.

- 단계가 전환될 때
- 사용자 승인을 기다릴 때
- 테스트 또는 외부 상태로 작업이 중단될 때
- 컨텍스트나 토큰 부족이 예상될 때
- 예외가 기획 단계로 되돌아갈 때

체크포인트에는 최소한 다음을 기록한다.

- 현재 사이클과 단계
- 승인된 범위와 미승인 범위
- Git HEAD와 작업 트리 상태
- 완료·미완료 TODO
- 마지막 검증 명령과 결과
- 변경하면 안 되는 사용자 파일
- 재개 시 첫 행동

## 7. 완료 정의

다음 조건을 모두 만족해야 한 사이클을 완료로 판단한다.

1. 승인된 기획과 TODO가 존재한다.
2. 모든 개발 TODO가 구현 및 읽기 전용 검수를 통과했다.
3. QA가 TODO, 예외, 회귀, 산출물 증거를 통과시켰다.
4. 정제 문서와 raw 기록이 저장됐다.
5. 체크포인트가 최종 상태를 가리킨다.
6. 사용자가 최종 결과를 승인했다.
