# 정적 카탈로그 변경 요약 구현 계획

상태: 사용자가 구현을 승인했으며 개발 중. 기준 제품 트리: `8352753584913b0b99a0bc635d6b58fb2ef2c5f5`.

## 목적과 범위

상위 설계 `Assets/Plan/TFTDataPipeline.md` §6.1의 매니페스트 변경 요약을 채운다. 이미 구현된 두 카탈로그의 상세 비교를 재사용하며, 자동으로 직전 패치를 추측하지 않는다.

- 데이터 관리 탭에서 새 카탈로그를 가져오기 전, 검증된 로컬 기준 카탈로그를 사용자가 선택할 수 있도록 한다. 선택은 필수가 아니며 기준이 없거나 선택하지 않은 경우 요약 없이 가져올 수 있다.
- 서로 다른 유효한 카탈로그를 비교할 때 기존 `CatalogDiffer`의 결과를 사용해 기물·시너지·아이템·증강 각각의 추가·변경·삭제 레코드 건수를 만든다. 이미지 변환과 정규화가 끝난 실제 게시 대상과 비교하며, 선택 당시 기준 identity와 해시를 고정한다. 기준과 대상의 세트·패치·원본 게임 버전·출처 프로필·내용 해시를 기록한다. 같은 카탈로그, 다른 세트나 출처 프로필, 유효하지 않은 기준은 허용하지 않는다.
- 새로 게시되는 카탈로그의 기존 `manifest.json`의 `previousPatchSummary`에 버전이 있는 제한된 구조의 요약을 저장한다. 기존 카탈로그 파일 및 해시는 바꾸지 않는다. 같은 카탈로그가 이미 존재해 재사용되면 기존 매니페스트를 그대로 유지하고 새 요약이 저장됐다고 알리지 않는다.
- 목록이나 상세 영역에서 기준과 요약을 보여준다. 문자열 길이·형식·필수 값·중복 키·건수 범위와 대상 연결을 검증하며 구형 자유 문자열과 미지원 형식은 안전하게 처리한다. 기준이 유효할 때 기존 비교 결과와 일치하는지 재계산한다. 기준이 없어 재계산할 수 없으면 저장된 비교 기록의 재검증이 불가능함을 알리고, 없거나 읽을 수 없는 경우에도 해당 상태를 알린다. 상세 변경은 기존 비교 화면을 사용한다.
- 실제 다운로드나 Riot 경기 API 호출은 이번 작업에 포함하지 않는다. 기존 카탈로그의 일괄 재작성이나 과거 패치 순서의 추론도 하지 않는다.

## 확인한 제약과 기획 검토

- `CatalogAssetWriter.NormalizeForContentSnapshot`은 `PreviousPatchSummary`를 빈 문자열로 정규화하므로 요약은 현재 카탈로그 내용 해시 계산에 포함되지 않는다. 별도 `manifest.json`의 무결성은 그 해시만으로 보장되지 않으므로 읽을 때 요약을 신뢰하기 전 검증해야 한다.
- 기획 당시 `PublishedCatalogLoader`는 `catalog.json`과 `manifest.json`을 함께 읽지만 후자의 요약 필드는 사용하지 않았다. 구현에서는 매니페스트의 요약을 별도로 읽어 검증한다. 이미 게시된 파일은 같은 내용으로 재가져와도 갱신되지 않는다.
- Antigravity 기획 A는 기준의 명시적 선택과 식별자·해시, 기존 비교 재사용, 실패 시 기존 파일 보존을 권고했다. 해시 포함 가능성은 미확인 가설이었고 위 코드 확인으로 보정했다. 원본: `AntigravityCollab/tasks/2026-11-07-static-change-summary/outputs/review.json`.
- GPT 기획 B는 동일한 기준 명시·무효 상태·기존 파일 보존을 요구하고 별도 기록을 제안했다. 별도 기록만으로는 매니페스트 요구를 충족하지 않으므로 새 게시 시 기존 매니페스트에 기록하는 안을 채택한다. 보정된 해시 계약을 전달한 재검토에서 B는 이 안이 타당하다고 판단하고 게시 대상 기준 재계산과 매니페스트 검증을 권고했다. 기존 데이터에는 소급 적용하지 않는다. B의 실제 모델·추론 설정은 확인하지 못했다.

## 완료 및 검수 조건

1. 기준 미선택·단일 카탈로그·동일 카탈로그·잘못된 기준, 기준 삭제·변경, 손상되거나 알 수 없는 요약을 명확히 처리한다. 비교 방향을 화면에 표시하고 패치의 전후 관계를 단정하지 않는다.
2. 합성 카탈로그로 네 종류의 추가·변경·삭제 수와 기준 식별자를 검증하고, 새 게시·동일 파일 재사용·게시 실패 시 기존 파일과 해시 보존을 확인한다. 예전 형식도 안전하게 읽혀야 한다.
3. 변경된 기능과 관련된 테스트를 우선 실행한다. 코드 검토에서 전체 기능에 큰 영향이 확인되면 전체 테스트를 추가한다. Unity 화면 검증이 필요하면 프로젝트의 소유 창 정리 절차를 따른다.
4. 독립 코드 검수와 QA를 거쳐 PR을 준비한다. 실제 외부 다운로드나 실제 데이터 검증은 실행 여부를 별도 구분한다.
