# 정적 비교의 구분자 충돌 조사

상태: 실제 비교기에서 합성 재현, 수정 전. 기준 main ba50db8. 제품 코드·기존 카탈로그·실제 API 변경 없음.

## 원인과 범위

`CatalogDiffer`는 관계 ID 목록·효과 사전·출처 목록을 각 항목에 포함될 수 있는 U+001F/U+001E를 구분자로 이어 붙인 후 문자열 동등성으로 비교한다. 도메인과 정적 검증기는 이 문자의 필드 내부 사용을 금지하지 않아 구분자와 실제 값의 경계가 모호하다. 이전/이후가 다른데 합쳐진 비교 문자열이 같으면 변경을 발견하지 못한다.

Unity의 실제 `CatalogDiffer.Compare`와 `CatalogValidator.Validate`에 다음 별개의 창작 카탈로그 쌍을 각각 넣었다. 각 이전·이후 카탈로그의 검증 오류는 0건이었고 실제 비교 결과의 변경 기물은 0개였다.

1. 서로 다른 두 효과 사전: 항목 2개와 항목 1개. probe: `Library/TftAnalyzerValidation/StaticDiffCollisionProbe.cs`.
2. 서로 다른 시너지 참조 목록: 두 ID와 하나의 ID. 참조 대상은 양 카탈로그에 모두 존재한다. probe: `Library/TftAnalyzerValidation/StaticDiffExtendedProbe.cs`.
3. 서로 다른 문서 출처 필드 2개: 같은 구분자로 연결된 문자열이 우연히 일치한다. 위 extended probe 사용.

모두 특수 제어문자를 의도적으로 포함한 합성 입력이다. 사용자의 실제 카탈로그에서 변경 누락이 발생했다거나 빈도가 높다고 결론 내릴 수 없다. 포함된 18.2 카탈로그의 효과 키·관계 ID 등 제한된 읽기 검사에서는 해당 문자가 발견되지 않았다. 출처 문자열과 다른 카탈로그까지 전수 확인한 결과는 아니다.

## 수정 설계 검토 항목

- 비교 동등성은 구분자 충돌이 없는 구조화 표현이나 형식별 원소 비교로 결정한다. 원문을 금지하거나 기존 카탈로그 파일을 고치지 않는다.
- 화면에 서로 다른 값을 동일하게 보이게 만들지 않도록, 원문 제어문자는 안전하게 구분되는 표시가 필요하다. 이전/이후 내부 자료구조에서 안전한 표현을 만들고, 모호한 연결 문자열을 사후 분리해 원래 배열로 추정하지 않는다.
- 관계 목록의 기존 순서 무관 계약, 효과의 키 정렬과 숫자 형식, 출처의 실제 의미·정렬 및 조회 시각만 다른 경우 무시하는 기존 계약을 보존한다. 델타의 필드명·정상 항목 추가/삭제/변경 및 새 형식의 UI 표시와 비교 방향도 함께 검증한다.
- 위 3가지 실패 예제와 구분자가 없는 일반 목록·사전·출처, 복수 값·빈 값·기존 schema/카탈로그 보존의 실제 회귀 테스트가 필요하다. 정확한 API·표현·UI 범위는 기획 A/B 검토와 사용자 승인 범위에 맞춰 확정한다.
