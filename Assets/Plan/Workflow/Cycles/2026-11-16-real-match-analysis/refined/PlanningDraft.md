# 실제 경기 분석 지원 기획 초안 (KI-003 후속)

상태: 초안, 기획 A/B 독립 검토 전. 기준 커밋 `ba49c69`. 작성: Master(Claude Opus 5.5).

## 목표

실제 Riot 경기가 분석에 쓰이도록 한다. 지금은 실제 수집 경기가 정상 관측으로 한 건도 저장되지 않아, 분석 기능이 합성 데이터로만 동작한다. 다음 신뢰 경계는 유지한다.

- 패치가 확인되지 않은 경기를 확정 패치 통계에 합치지 않는다(2026-11-05 사용자 결정).
- 증강 미제공을 "증강 없음"(빈 목록)으로 바꾸지 않는다.
- 원본 응답, 경기 ID, 플레이어 식별자, API 키를 저장하지 않는다.
- 최소 표본 100건 미만의 비율 지표는 표시하지 않는다.

## 현재 사실

- 실제 수집 5건은 상세를 받았으나 저장 0건이었다. 사용자 승인 아래 단일 진단을 두 번 했고, 두 경기 모두 세트18·큐1100이 일치했다. 그러나 `game_version`이 기존 숫자 패턴과 맞지 않았고, `data_version`은 1~5 밖이었으며, 참가자 `augments`가 없었다. 진단은 범주만 기록해 실제 값은 모른다. 최초 5건과 같은 경기인지도 미확인이다.
- 정상 저장 조건(`MatchAnonymizer`): `data_version`이 정확히 `"2"`, `game_version`이 `Version x.y.z[.w]` 형식이고 그 릴리스가 선택 카탈로그와 일치, 참가자마다 `augments` 배열이 명시돼 있어야 한다. 하나라도 어기면 저장하지 않는다.
- 불완전 수신 기록(PR #30, 병합됨): 정상 조건을 못 맞춘 응답에서 읽을 수 있는 값만 별도 저장한다. 최대 128건, 건당 256KiB, 자동 삭제 없음. 조회·삭제만 하며 정상 관측·집계·CSV에는 쓰지 않는다. 저장하는 값은 세트 번호, 큐, 참가자별 순위·마지막 라운드·기물(ID, 성급, 아이템)·시너지(ID, 단계)·증강이다. 각 값에는 상태(값/누락/null/빈 배열/형식 오류)와 의미(확인/미검증)가 붙는다. `game_version`과 `data_version` 값은 저장하지 않는다.
- 조합 기준(PR #29 이후): 조합은 기물 목록과 활성 시너지로 구분한다. 아이템과 증강은 조건 필터다. 최소 표본 하한은 100건이다.
- 증강 정책: 승인된 증강 분류 자료가 없어 증강 관련 비율은 이미 차단돼 있다. `MetricPolicy`는 빈 증강 목록에는 제한을 걸지 않으므로, 미제공을 빈 목록으로 바꾸면 이 차단을 우회하게 된다.
- 공개 근거: Riot 문서는 `data_version` 1·2만 설명한다. 외부 개발자 제보(Riot 개발자 관계 이슈 #1185: 세트18·큐1160에서 숫자 패치를 판별할 수 없는 `game_version`과 `augments` 누락, #1171 댓글: 세트18·큐1100의 `game_version`)는 Riot의 확인 답변이 없다.

## 핵심 문제

1. **패치 식별**: `game_version`을 숫자 릴리스로 읽지 못하면 카탈로그와 연결할 수 없다.
2. **데이터 버전**: `"2"`가 아닌 버전의 필드 의미가 검증되지 않았다.
3. **증강 미제공**: 증강 조건·지표를 계산할 수 없다.
4. **표본 규모**: 불완전 기록 상한 128건은 최대 1,024 참가자 행이다. 조합별 표본 100건에 도달하기 어려워, 그대로는 분석 용도로 쓸 수 없다.

## 선택지

- **A. 형태 진단 우선**: 사용자가 승인한 소수 경기만 받아 `game_version`·`data_version`의 형태를 비식별로 기록한다. 결과를 보고 B 또는 C를 고른다.
- **B. 정상 경로 확장**: 실제 형식이 결정적으로 릴리스로 해석되고, 새 `data_version`의 필수 필드 의미가 기존과 같다는 근거가 있으면 해석 규칙과 지원 버전을 추가한다. 증강 미제공은 관측 스키마의 별도 상태로 저장하고 증강 조건·지표는 fail-closed한다. 이 경우 실제 경기가 확정 패치 통계에 정상 합류한다.
- **C. 별도 참고 분석**: 패치를 끝내 확인할 수 없으면 세트·큐 단위의 "패치 미확인 참고 통계"를 별도 범위로 제공한다. 확정 패치 통계·CSV와 섞지 않고, 화면에 패치 미확인·의미 미검증을 표시하며, 증강 지표는 차단한다. 저장 상한과 중복 처리를 분석 용도로 재설계해야 한다.
- **D. 보류**: 공식 근거가 생길 때까지 현행을 유지한다.

## 권장안

1단계로 A를 수행하고, 그 결과에 따라 2단계(B 또는 C)를 별도로 기획·승인한다. 실제 값을 모르는 상태에서 B나 C를 설계하면 근거 없는 추정이 되기 때문이다. 증강 미제공 상태 저장은 B와 C 모두에 필요하므로 2단계의 공통 설계로 다룬다.

## 1단계 범위 (이번 승인 요청 대상)

- **기록 항목(비식별)**: `data_version`은 1~3자리 정수일 때만 값을, 아니면 범주를 기록한다. `game_version`은 형태 서명만 기록한다. 숫자는 `9`, 영문자는 `a`로 바꾸고 길이를 제한하며, `Version ` 접두 여부, 숫자 그룹 수, 앞의 두 숫자 그룹 값(릴리스 후보), 괄호·태그 구간 존재 여부를 남긴다. 그 밖에 세트 번호와 큐, 참가자 `augments`의 상태(배열/누락/null/빈 배열)를 기록한다.
- **저장하지 않는 것**: 원본 응답, `game_version` 원문, 경기 ID, PUUID·이름, API 키.
- **요청 상한**: 사용자가 정한 경기 수(제안: 최대 20경기)와 그에 맞는 목록·상세 요청 수. 401·429·5xx는 즉시 중단하고 재시도는 수동으로만 한다. 키는 기존 환경 변수 방식을 쓰며 기록하지 않는다.
- **결과물**: 형태별 분포 보고서(경기 수, `data_version` 값·범주별 개수, `game_version` 형태 서명별 개수, 릴리스 후보 값, 증강 상태 분포)와 결과를 바탕으로 한 2단계 권고.
- **검증**: 합성 응답으로 실패 테스트부터 작성한다. 원문·식별자 sentinel이 보고서와 로그에 남지 않는지, 요청 상한·중단·취소, 기존 관측·불완전 기록·카탈로그가 변하지 않는지를 확인한다. 실제 호출은 합성 검증과 사용자 승인 뒤 한 번만 한다.

## 사용자 결정이 필요한 질문

1. 1단계의 실제 API 호출을 허용할지와 경기 수 상한.
2. 패치를 끝내 확인할 수 없을 때 C(세트 단위 참고 통계)를 원하는지, D(보류)를 원하는지.
3. 증강 지표가 계속 막혀 있어도 조합·아이템 통계만으로 사용할 가치가 있는지.

## 검토 요청

- 기획 A(Antigravity): 제품 범위, 사용자 가치, 정책·개인정보 위험, 선택지와 권장 순서의 타당성.
- 기획 B(Claude): 기술 구조, 형태 서명의 비식별성, 실패·취소·복구, 테스트 가능성, 완료 조건, 2단계로 넘길 계약.
- 공통 필수 점검(워크플로 §3.1): fail-closed 정책의 실데이터 통과 경로, 집계 입도와 최소 표본의 달성 가능성, 상위 설계 대비 하위 계약의 일관성.
