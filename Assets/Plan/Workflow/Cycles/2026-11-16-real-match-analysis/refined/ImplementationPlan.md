## 목표

실제 Riot 경기 응답의 `game_version`·`data_version`·증강 제공 상태와 조합 다양성을 비식별 집계로 측정한다. 그 결과를 아래 분류표로 판정해 2단계 기획의 입력으로 쓴다.

## 범위

- 포함: 수집 경로와 분리된 진단 클래스, 전송 예산 래퍼, 토큰 단위 판독기, 비식별 서명 변환, 집계 보고서와 원자적 게시, Editor 메뉴 진입점 1개, 합성 테스트, 승인 조건 충족 후 실제 1회 실행, 결과 보고서의 사이클 폴더 보존.
- 제외: 관측·불완전 기록·격리 보고서·카탈로그·인덱스 쓰기, `MatchAnonymizer.Read` 호출과 후보·관측 객체 생성, 분석·CSV·UI 변경, 2단계 설계, 최초 실패 5건의 재현(경기 ID를 저장하지 않아 대응할 수 없다).

## 설계

### 위치와 입력

- `Assets/TFTAnalyzer/Editor/Diagnostics/`에 커밋한다. `Persistence` 저장소 타입을 참조하지 않으며, 생성자·필드를 리플렉션으로 검사하는 테스트를 둔다.
- 진단 클래스의 의존성은 전송(`IRiotApiTransport`), 키 제공자, seed 제공자, 보고서 sink다.
- 불변 입력: region, 대상 큐, 세트 번호, 선택 카탈로그의 릴리스(앞 두 그룹), 종류별(기물·아이템·시너지·증강) 정적 ID 집합의 복사본.
- 메뉴 진입점은 이미 검증된 로컬 카탈로그를 읽기 전용으로 로드해 위 입력을 만든다. 가져오기·`Upsert`·`ObservationStore` 호출은 없다. 카탈로그가 없거나 세트·릴리스가 맞지 않으면 네트워크 전에 중단한다.
- 기존 `RiotApiClient`의 자동 재전송과 `MatchCollectionService`의 계속 진행 정책을 거치지 않는다.

### 전송 예산과 중단

- 사전 조건(네트워크 전 확인): 사용자의 키 재설정 알림, 키 형식 점검, 그리고 확인 대화상자에서 사용자가 "키 갱신 후 Unity를 재시작했다(환경 변수 반영)"와 "진행 중인 경기 수집이 없다"를 확인한다. 기존 코드에는 수집 실행 여부를 알 공유 상태가 없고, 수집 경로를 고치지 않기 위해 대화상자로 판정한다. 하나라도 어긋나면 시작하지 않는다.
- 실행 중에는 `EditorApplication.LockReloadAssemblies`로 도메인 리로드를 막고 `finally`에서 해제한다.
- seed는 첫 1개만 쓴다. 목록 1회(`count=20`), 상세 최대 20회, 요청마다 시도 1회. 요청 사이 간격은 1.2초 이상으로 고정해 개발 키 한도 안에 둔다(21회 약 25초).
- 실제 응답 429(Retry-After 포함), 401·403, 5xx, 전송 오류에서 즉시 중단한다. 404도 중단하되 목록 404와 상세 404의 사유 코드를 나눈다.
- 다른 큐 경기도 상세 상한 20에 포함하고, 보고서는 큐별로 나눈다.
- 실행 소모 규칙: 실행 1회는 조기 중단을 포함한 실행 1번이다. 보고서 없이 끝난 실행도 소모로 본다. 다만 첫 목록 요청이 401·403으로 끝나 상세를 하나도 받지 못하면 소모하지 않은 것으로 보고, 사용자가 키를 다시 확인한 뒤 한 번 더 실행할 수 있다.
- 보고서에 목록·상세별 물리 전송 수와 중단 단계를 남긴다.

### 판독기

- 기존 `StrictSyntaxReader`·`BoundedInput`을 재사용하는 토큰 단위 판독기로 필요한 필드만 읽는다. 공용 파서의 가시성을 바꾸면 `MatchAnonymizer` 회귀 테스트를 실행한다.
- 조합 다양성 계산을 위해 참가자 하나의 `character_id`·`tier_current`만 일시 버퍼에 두고, 참가자 처리가 끝나면 지운다.

### 비식별 서명 규칙 (`game_version`, `data_version` 공통)

1. JSON 타입(문자열·정수·null·기타·누락)을 먼저 기록한다.
2. 문자열은 유니코드 범주로 치환한다. 글자→`a`, 숫자→`9`, 공백→`_`, 허용 구두점 `. ( ) [ ] < > / : -`는 유지, 그 밖은 `?`.
3. 영숫자의 최대 연속(순수 글자·순수 숫자·혼합 모두 포함)이 6자 이상이면 `{x:6-8}`, `{x:9-16}`, `{x:17-32}`, `{x:33-64}`, `{x:65+}`로 접는다.
4. 하이픈으로 이어진 영숫자 구간이 2개 이상이면(GUID 형태 등) 전체를 길이 구간으로 접는다.
5. 변환 결과를 64자에서 자르고 잘림 여부를 기록한다.
6. 숫자 그룹 원값은 앞의 두 그룹(릴리스 후보)만, ASCII 숫자 1~3자리일 때만 남긴다. 나머지 그룹은 자릿수만 남긴다.

접기 규칙으로 `Version` 같은 고정 단어도 길이 구간이 되므로, `Version ` 접두 여부는 별도 bool로 기록한다.

### 기록 항목 (집계만, 경기별 행·순서·시각 없음)

- 큐별 경기 수, 중단 여부·단계·사유 코드, 목록·상세별 물리 전송 수.
- 두 필드의 타입·서명별 개수, `Version ` 접두 여부별 개수, 앞 두 숫자 그룹 원값(1~3자리)별 개수.
- 기존 `game_version` 정규식 일치 여부별 개수, 선택 카탈로그 릴리스와의 일치 여부별 개수.
- 필수 필드의 존재·타입 행렬별 개수. 대상 필드: `metadata.match_id`, `metadata.data_version`, `info.game_version`, `info.tft_set_number`, `info.queue_id`, `info.participants`(개수), 참가자의 `placement`, `last_round`, `units[].character_id`, `units[].tier`, `units[].itemNames`, `traits[].name`, `traits[].tier_current`, `augments`. 값은 기록하지 않는다.
- 경기 단위 증강 상태(전원 제공/전원 없음/혼합)별 개수.
- 종류별 카탈로그에 없는 정적 ID 개수(ID 값은 기록하지 않음).
- 조합 다양성(대상 큐만): 조합 지문 v2와 같은 정규화(기물 ID 중복 유지 정렬, 성급·아이템·증강 제외, `tier_current>0`인 시너지만 중복 없이 정렬)를 원시 ID로 적용한다. 고정 키는 제외 보드 수, 총 보드 수, 고유 조합 수, 1회만 나온 조합 수, 상위 5개 빈도, 빈도의 빈도 분포다. 조합 내용과 ID는 기록하지 않는다. 이 값은 seed 1명의 최근 경기에서 나온 상관된 표본이므로 다양성의 하한 참고치일 뿐 대표 표본이 아니다.

### 보고서

- 위치: `Library/TftAnalyzerDiagnostics/match-shape/`. 저장소 루트(`Library/TftAnalyzerStore`, `rootOverride` 포함)와 Assets 밖이어야 하며 테스트로 확인한다. reparse point가 있는 경로는 거부한다.
- 임시 파일에 쓴 뒤 원자적으로 이동한다. 상태(완료/취소/중단 사유)와 partial 여부를 넣는다. 도메인 리로드나 취소 시에는 보고서가 없거나 partial이다.
- 게시 전에 허용목록 스키마(고정 키·enum·정수·서명 문자 집합)로 검증한다.

### 결과 분류

대상 큐 표본 수를 n, 기준을 k=10으로 한다. 아래 순서로 처음 해당하는 분류를 쓴다.

1. partial 중단이거나 n<k이면 **결정 불가**.
2. `game_version` 서명이 둘 이상이면 **결정 불가**.
3. 앞 두 그룹에서 릴리스를 결정적으로 추출할 수 없거나 선택 카탈로그와 일치하지 않으면 **C/D 판정**.
4. 나머지는 **형태 조건 충족(외부 근거 대기)**.

`data_version` 서명 수는 분류 조건이 아니라 보고 항목이다.

- "형태 조건 충족"만으로 B(정상 경로 확장)가 되지 않는다. 새 `data_version` 의미에 대한 공식 또는 동등한 외부 근거가 있어야 B 후보가 된다.
- 관측되지 않은 형태의 95% 상한은 실제 대상 큐 n으로 3/n을 계산해 보고서에 적는다.
