# Antigravity 기획 A 자동 호출 제안

2026-10-19. 최초 제안과 후속 적용 기록. 확정된 사용자 결정은 기획 A=Antigravity, 기획 B=GPT다.

## 현재 적용 범위

[현재 Task6](tasks/2026-10-19-task6-planning/result.md)에 실제 Antigravity A와 GPT B의 동일 입력 검수를 적용했다. CLI plan 모드에 비밀값 없는 기획 문서만 전달한 단발 실행은 성공했고, [진입점](../AgentScripts/Invoke-AntigravityPlanningReview.py)은 입력 검증 dry-run을 확인했다. 강제 도구 제한은 입증하지 못했으며 일반 격리 자동화·예약은 활성화하지 않았다. SDK는 별도 API 키 요구로 전송 전에 중단했다. 아래는 최초 제안으로, custom agent의 도구 제거 등 미검증 항목을 현재 동작으로 읽지 않는다.

## 목적과 선택

Codex가 기획 검수 입력을 준비하고 Antigravity를 한 번 호출해 결과를 회수한다. GPT는 같은 자료를 독립 검수하고 Codex가 두 결과를 통합한다. 제품 구현과 Unity 실행은 Codex가 계속 맡는다. 기획 승인은 기존대로 사용자에게 있다.

첫 연결은 **공식 Antigravity CLI(`agy`)의 비대화형 실행**을 사용한다. 별도 플러그인이나 MCP 서버 없이 로컬 runner로 연결하는 제안이다. SDK는 도구 제한을 CLI 설치본에서 검증할 수 없을 때 검토할 대안이며, MCP는 다른 호출자가 필요해질 때 별도 검토한다. IDE 화면의 버튼·키보드 자동 조작은 선택하지 않는다. CLI는 단발 요청·JSON 결과·구조화 출력·명시 모델·사용량 기록을 제공한다. [공식 비대화형 실행 문서](https://www.antigravity.google/docs/cli/headless/)

제안 작성 당시에는 PATH 및 기본 경로에서 CLI를 찾지 못했다. 이후 사용자의 agy 실행 후 공식 기본 경로에서1.4.2를 확인하고 모델 조회·상수 응답 시험을 통과했다. 공식 Windows CLI 기본 경로는 `%LOCALAPPDATA%/agy/bin`이다. [공식 설치 안내](https://www.antigravity.google/docs/getting-started/)

## 역할과 전달 단위

| 담당 | 입력과 책임 | 결과 |
|---|---|---|
| Codex 조정 | 기준 커밋과 미커밋 입력 파일 해시 고정, 필요한 자료 복사 | 동일 snapshot과 역할별 요청 |
| 기획 A: Antigravity | 제품 가치·정책·범위·표본 현실성·누락 요구사항 | 근거가 있는 위험·수정 권고 |
| 기획 B: GPT | 동일 snapshot의 구조·예외/복구·검증·완료 조건 | 구현 가능성·검증 누락 |
| Codex 통합 | 두 검수의 공통점·충돌·실행 증거 필요 사항 판단 | 정제 기획안과 사용자 승인 요청 |

기획 A/B는 상대방의 이번 초안을 읽기 전에 1차 검수를 마친다. 같은 커밋이어도 dirty 파일이 다르면 다른 입력이다. 기존 Task6의 두 GPT 기획 검토를 Antigravity 실행 이력으로 바꾸지 않는다.

전달 폴더 제안:

```text
AntigravityCollab/tasks/<task-id>/
  request.md             # 실제 기획 A 요청
  manifest.json          # 기준 commit, 원본 경로, 복사본 SHA-256, prompt 버전
  inputs/                # 필요한 계획과 관련 코드 발췌만 복사
  outputs/review.json    # 검증한 구조화 응답
  outputs/runtime.json   # CLI 버전, 요청/확인 모델·추론, 시간·사용량·종료 상태
  result.md              # Codex가 정리한 공개 검수 결과 또는 실패 이유
```

요청·응답은 이 폴더를 통해 보존한다. 전송 자료는 `inputs/` 복사본과 `request.md`를 합친 UTF-8 텍스트다. 원본 경로를 전달해 프로젝트 전체를 다시 탐색하게 하지 않는다. API 키·개인 seed·식별 가능한 경기 응답은 복사하지 않는다. 과거 대화 전체·Library 전체·숨겨진 추론은 입력/공개 기록에 넣지 않는다.

## 호출과 결과 회수

1. 준비 단계에서 CLI 버전과 설치본의 옵션·모델 목록을 확인하고 실제 사용할 모델 ID를 선택한다. 모델을 찾지 못하면 다른 모델로 조용히 대체하지 않는다. 초기 로그인은 사용자 브라우저에서 한 번 수행한다. 계정 인증값을 프로젝트에 저장하지 않는다.
2. 계획 검수가 필요한 시점에 Codex가 입력 snapshot을 만든다. 기본 입력 상한은 UTF-8 48KiB, 응답은 주요 발견10개/총4,000자 이내로 제안한다. 상한을 넘으면 필요한 절을 골라 별도 요청으로 명시하며 자료를 몰래 잘라 보내지 않는다. 바이트 상한은 토큰 상한과 구분한다.
3. runner는 작업 폴더를 시작 위치로 사용하고 별도 `planning-a` agent 구성을 선택한다. 도구·MCP·추가 에이전트·외부 검색 없이 제공 텍스트만 검토하는 구성을 목표로 한다. [공식 custom agent 도구 구성](https://www.antigravity.google/docs/subagents/)
4. `--input-format stream-json`, `--output-format stream-json`, `--agent`, 명시적인 `--model`/`--effort`, `--json-schema`, `--print-timeout`을 사용할 계획이다. 시작 `init`의 도구 목록·agent·모델을 확인한 뒤 요청을 보낸다. 도구가 남아 있거나 설정이 다르면 원본 자료를 전송하지 않고 실패 처리한다. 설치본에서 이 순서를 지원하는지도 시험 대상이다.
5. 표준 입력에 `{ "event": "user", "message": { "content": "<준비한 요청과 자료>" } }` 한 건만 보내고 입력을 닫는다. 긴 요청을 쉘 명령 문자열에 넣지 않고 child process의 입력 스트림으로 전달한다. 표준 출력·오류를 동시에 소비하며, 종료 후에만 출력을 읽어 pipe가 막히는 구현을 피한다.
6. 기본 제한은 CLI3분/상위 프로세스3분30초다. 기한 초과 시 runner가 만든 정확한 child process만 취소·종료하고 실패를 기록한다. 사용자 Antigravity 앱이나 Unity 프로세스를 종료하지 않는다. 종료 코드를 포함해 마지막 `result.status == SUCCESS`, 구조화 응답 형식, task ID와 입력 해시 일치를 모두 확인한다. CLI 성공과 검수의 수정 요청 판정은 별개다.
7. Codex가 결과 파일을 기록한다. 응답에는 `taskId`, `inputDigest`, `verdict`, `findings`(심각도/근거 경로·절/영향/권고), `unverified`를 요구한다. 빈 답·중간 답·권한 거부로 누락한 근거는 완료로 취급하지 않는다.
8. 실행 구성과 terminal 결과에서 모델·추론·시간·사용량을 확인 가능한 만큼 기록한다. 요청값과 CLI가 확인한 값을 구분하고 제공되지 않은 정보는 미확인으로 남긴다. 모델 자기소개를 실제 모델 증거로 삼지 않는다. 숨겨진 추론·임의 도구 payload·인증 정보가 담길 수 있는 진단 로그 전체를 공개 저장하지 않는다.

도구를 제거하는 설정은 설치본에서 먼저 검증해야 한다. 프롬프트의 '읽기 전용' 문구나 실행 전후 해시만으로 접근 차단이 구현됐다고 주장하지 않는다. CLI에서 충분한 제한을 입증할 수 없으면 자동화를 활성화하지 않고 SDK의 명시적 도구 제한을 검토한다. [SDK 도구 제한](https://antigravity.google/docs/sdk/tools)

## 호출 빈도와 비용

- 시점은 새 기획 또는 해당 기획의 실질적 변경 때다. 5분 예약·상시 감시·앱 종료 후 자동 깨우기는 만들지 않는다. Codex가 작업 중일 때 runner를 호출하는 방식이다. Hermes 예약 재개와 무관하다.
- 기본 검수는 각자 한 번이다. 입력 해시·prompt 버전·모델/추론·runner 구성이 모두 같은 완료 결과가 있으면 재사용 여부를 명시하고 새 실행으로 세지 않는다.
- 재검토가 필요하면 쟁점과 바뀐 자료만 전달한다. 자동 반복 재검수는 만들지 않는다. 로그인·사용량·네트워크 오류 때 자동 재시도나 GPT 대행으로 기획 A 완료를 기록하지 않는다.
- CLI 결과의 실제 token usage를 기록하고 입력 바이트·실행 횟수·시간·재작업과 함께 비교한다. 구독 한도를 API 단가로 환산하지 않는다.

## 구현·활성화 순서와 완료 증거

1. CLI 설치 또는 기존 실행 경로 확인, 사용자 로그인, 설치본의 모델/옵션 확인.
2. 프로젝트 안에 작은 runner와 구조화 응답 schema, 도구 없는 `planning-a` 구성을 준비. 현재 단계에서는 이 코드나 설치를 수행하지 않았다.
3. 가짜·비밀값 없는 작은 계획으로 단발 smoke 실행. 도구 목록 비어 있음, 정확한 모델 구성, 구조화 결과, 시간/사용량과 폴더 기록 확인.
4. 인증 없음·알 수 없는 모델·권한 구성 불일치·시간 초과·중간 출력·깨진 JSON·입력 변경을 실패로 처리하는 확인. 사용자 파일/프로세스 보존도 대조.
5. 현재 Task6 입력을 기준으로 Antigravity 기획 A를 실제 실행하고, 기존 GPT 기획 B가 같은 입력을 검수했는지 확인한다. 다르면 필요한 변경분만 GPT B에 재검수한다.
6. 결과 통합 후 활성 상태와 증거를 README/체크포인트에 기록. 실제 성공 전에는 '자동 연결됨'으로 바꾸지 않는다. 제품 검증·사용자 기획 승인은 기존 워크플로대로 별도 수행한다.

현재 실행 증거는 경로/모델 조회·상수 요청 응답·문서 링크/형식 확인이다. 별도 GPT의 [구현 가능성 점검](2026-10-19-proposal-check.md)은 중대한 누락 없음으로 응답했으며 Antigravity 기획 A 검수를 대행한 것이 아니다. 첫 두 초기화의 도구 제한 점검은 실패했고, 별도로 상수 응답만 시험해 CLI 연결 성공을 확인했다. 실제 기획 검수·접근 제한·사용량 절감은 여전히 미검증이다.
