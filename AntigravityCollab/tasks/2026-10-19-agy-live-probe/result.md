## 도구 제한 점검은 별도 미해결

초기 점검 두 차례는 시작 이벤트의 전체 도구 목록을 확인한 뒤 요청을 보내지 않고 종료했다. 첫 구성이 tools 빈 목록이었고, 두 번째는 프로젝트 밖 임시 폴더에서 완료 도구만 명시했으나, 시작 이벤트에는 파일·명령·브라우저·MCP 도구가 계속 노출됐다.

- [첫 초기화 점검](outputs/probe-runtime.json)
- [두 번째 초기화 점검](outputs/probe-runtime-attempt2.json)

이에 실제 자료를 넣는 기획 검수와 연결 시험을 분리했다. 마지막 시험의 상수 요청은 성공했고 도구 실행도 관측되지 않았지만, 이는 접근 차단 설정이 적용됐다는 증거가 아니다. runtime의 `toolRestrictionVerified=false`, `workflowActivated=false`를 그대로 보존한다. 원인을 확인하기 전 실제 프로젝트 자료 검수를 자동 활성화하지 않는다.

이번 결과는 Codex가 새 agy 프로세스를 직접 실행해 응답을 받은 증거다. 사용자가 켜 둔 대화에 메시지를 주입한 것이 아니며 예약·상시 감시·Codex 자동 깨우기도 등록하지 않았다. 다음은 CLI 설치본의 agent/도구 제한 적용 경로를 확인하거나 SDK 제한을 검토한 뒤 현재 기획 자료의 검수를 연결하는 것이다.
