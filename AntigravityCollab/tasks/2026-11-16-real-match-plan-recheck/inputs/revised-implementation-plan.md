# 1단계 구현 계획: 실제 경기 형태 진단

상태: 수정안(기획 A/B 1차 검토 반영), A·B 재검토 후 사용자 승인 대기. 기준 `ba49c69`.

2026-11-16 사용자 결정: 실제 Riot API 실행은 N=20(목록 1회, 상세 최대 20회)으로 허용한다. 단, 현재 API 키가 만료돼 사용자가 키를 재설정했다고 알린 뒤에만 실행한다. 수정안은 A·B 재검토를 거쳐 승인받는다. 2단계(정상 경로 확장 또는 별도 참고 분석)는 이 계획의 범위가 아니다. 근거: [통합 검토](PlanningReview.md), [최초 초안](PlanningDraft.md).

## 목표

실제 Riot 경기 응답의 `game_version`·`data_version`·증강 제공 상태와 조합 다양성을 비식별 집계로 측정한다. 그 결과로 2단계를 사전에 정한 규칙에 따라 B·C·D 중 하나로 판정한다.

## 범위

- 포함: 수집 경로와 분리된 진단 클래스, 전송 예산 래퍼, 토큰 단위 판독기, 비식별 서명 변환, 집계 보고서와 원자적 게시, Editor 메뉴 진입점 1개, 합성 테스트, 사용자 승인 후 실제 1회 실행.
- 제외: 관측·불완전 기록·격리 보고서·카탈로그·인덱스 쓰기, 분석·CSV·UI 변경, 2단계 설계, 최초 실패 5건의 재현(경기 ID를 저장하지 않아 대응할 수 없다).

## 설계

### 위치와 의존성

- `Assets/TFTAnalyzer/Editor/Diagnostics/`에 커밋한다. 의존성은 전송(`IRiotApiTransport`), 키·seed 제공자, 호출자가 넘기는 불변 값(세트 번호, 선택 카탈로그의 릴리스 앞 두 그룹), 보고서 sink 하나로 제한한다.
- `Persistence` 저장소 타입(`ObservationStore`, `IncompleteMatchStore`, `CatalogIndex` 등)을 참조하지 않는다. 생성자·필드를 리플렉션으로 검사하는 테스트를 둔다.
- 기존 `RiotApiClient`의 자동 재전송과 `MatchCollectionService`의 계속 진행 정책을 거치지 않는다.

### 전송 예산과 중단

- seed는 첫 1개만 쓴다. 목록 요청 1회(`count=N`), 상세 요청 최대 N회, 요청마다 시도 1회.
- 2xx가 아닌 첫 응답(401·403·404·429·5xx)이나 전송 오류, 사전 `rate_limited` 상태에서 즉시 중단한다. 404도 중단으로 정한다.
- 네트워크 전에 키 사용 가능 여부를 점검한다. 키 값은 어디에도 기록하지 않는다.
- 다른 큐 경기도 상세 상한 N에 포함하고, 보고서는 큐별로 나눈다.
- "실제 실행 1회"는 조기 중단을 포함한 실행 1번을 뜻한다.

### 판독기

- 기존 `StrictSyntaxReader`·`BoundedInput`을 재사용하는 토큰 단위 판독기로 필요한 필드만 읽는다. 후보·관측 객체를 만들지 않는다.
- 공용 파서의 가시성을 바꾸면 `MatchAnonymizer` 회귀 테스트를 실행한다.

### 비식별 서명 규칙 (`game_version`, `data_version` 공통)

1. JSON 타입(문자열·정수·기타·누락)을 먼저 기록한다.
2. 문자열은 유니코드 범주로 치환한다. 글자→`a`, 숫자→`9`, 공백→`_`, 허용 구두점 `. ( ) [ ] < > / : -`는 유지, 그 밖은 `?`.
3. `a`·`9`가 8자 넘게 이어지면 `{a:길이구간}`·`{9:길이구간}`으로 접는다.
4. 변환 결과를 64자에서 자르고 잘림 여부를 기록한다.
5. 숫자 그룹 원값은 그룹이 1~3자리일 때만 남기고, 그 밖은 자릿수만 남긴다.

### 기록 항목 (집계만, 경기별 행·순서·시각 없음)

- 큐별 경기 수, 중단 여부와 사유 코드.
- 두 필드의 타입·서명별 개수, 숫자 그룹 원값(1~3자리)별 개수.
- 기존 `game_version` 정규식 일치 여부별 개수, 선택 카탈로그 릴리스와의 일치 여부별 개수.
- 필수 필드의 존재·타입 행렬별 개수.
- 경기 단위 증강 상태(전원 제공/전원 없음/혼합)별 개수.
- 종류별 카탈로그에 없는 정적 ID 개수(ID 값은 기록하지 않음).
- 정상 경로 첫 실패 코드별 개수(참고용).
- 조합 다양성: 정확히 같은 조합(기물 목록 + 활성 시너지)의 빈도 분포. 고유 조합 수와 상위 빈도 값만 기록하고 조합 내용·ID는 기록하지 않는다.

### 보고서

- 위치: `Library/TftAnalyzerDiagnostics/` 아래, 저장소 루트·Assets와 분리.
- 임시 파일에 쓴 뒤 원자적으로 이동한다. 상태(완료/취소/중단 사유)와 partial 여부를 넣는다. 도메인 리로드나 취소 시에는 보고서가 없거나 partial이다.
- 허용목록 스키마(고정 키·enum·정수·서명 문자 집합)로 게시 전에 검증한다.

### 사전 판정 규칙

- **B 후보**: 모든 대상 큐 표본이 결정적으로 릴리스를 추출하고 선택 카탈로그와 일치하며, 새 `data_version` 의미에 대한 공식 또는 동등한 외부 근거가 있을 때만.
- 그 밖에는 C 또는 D로 판정하고, 둘 중 선택은 사용자 결정을 따른다.
- 보고서에 N=20이면 관측되지 않은 형태의 95% 상한이 약 14%임을 함께 적는다.

## 2단계 기획 진입 조건

- 1단계 보고서와 사전 판정 결과.
- 증강 미제공 정책표: 평균 순위, Top4·1위 비율, 상대 지표, CSV별 처리.
- 표본 규모 분석: 1단계 조합 다양성 실측을 바탕으로 지표 입도별 n≥100 달성에 필요한 경기 수.
- B 계약: 릴리스 매핑 표(출처·버전 관리, 불일치 fail-closed), 버전별 필수 필드 스키마를 갖춘 `data_version` 허용목록, 증강 3상태, 관측 schemaVersion 2와 schema1 읽기 호환, strict 지문 v3, 집계 캐시 무효화, null→빈 목록 변환 제거, 차단 사유 코드, CSV 열·UI 표시, 불완전·격리 기록 비승격.
- C 계약: 목표 표본에서 역산한 별도 저장소 상한, 보존·삭제 정책, 패치 혼합 시 정적 ID 바인딩, 로컬 비밀 기반 중복 해시 여부, 확정 통계·CSV와의 물리적 분리.
- 공통: 상위 계약(2026-11-05 결정, `MetricPolicy` 하한 100)과 하위 계약의 대응표.
