# 실제 경기 수집 실패 원인 분석 및 수정 후보

상태: 초안. 사용자 요청: 과거 경기 5건 실패의 원인을 파악하고 워크플로에 따라 수정·검증·PR. 같은 오류의 근거 없는 반복을 중단한다.

목표: 실제 실패의 정확한 원인을 식별하고 확인된 계약에 한해서 수정을 계획한다. 현재 실패한 5건의 개별 원인을 확보하지 못했고, 각 진단은 요청 시점의 최신 경기 한 건을 읽었고 서로 같은 경기인지 확인하지 않았다. 결과를 5건 전체에 대입하지 않는다. 사용자 키·PUUID·Match ID·응답 본문·원문 필드값·임의 예외 문구를 협업/로그/저장소에 싣지 않는다.

진단: 통제된 인메모리 진단에서 고정된 참/거짓만 출력. `metadata.data_version`은 문자열이며 1·2 어느 쪽도 아님, 참가자 `augments`가 하나 이상 배열이 아님. 누락·null·다른 타입 구분은 아직 미확인. 나머지 참가자 placement/last_round/units/traits는 확인된 타입. 경기 8명, metadata/info 필수필드 타입은 확인됐다. 사용자 환경의 현재 카탈로그는 세트18/18.2/16.18.1. 이것이 경기와 같은 버전인지는 확인하지 않았다.

제안: 먼저 공식 TFT Match API 형식과 안전한 진단만으로 데이터 버전·모드/세트·배열 상태를 정해진 범주만으로 식별한다. 원본 응답·식별자·자유 입력 및 예외 메시지는 저장/출력하지 않는다. 실데이터 재요청 전 합성 응답으로 누수·오작동/종료 조건을 검증한다. 비결정 또는 같은 오류 반복 시 중단하고 사용자에게 보고한다. 새 실데이터 조회 횟수·범위를 승인안에 명시한다.

확인한 사실에 맞는 최소 수정만 선택한다. 예를 들어 비대상 경기면 파싱 전에 신뢰 가능한 최소 metadata로 분류해 제외하고, 실제 지원 형식이 확인되면 근거 있는 스키마/데이터 버전만 지원한다. 새 형태의 안전하지 않은 식별자·unknown ID·Legend·n100 가드를 완화하지 않으며 검증되지 않은 null/누락을 빈 증강으로 추정하지 않는다. 계획 검토 중 이 선택이 성급하면 진단/수정 계획을 분리한다.

검증: 합성 fixture로 실패 재현→최소 수정→관련 GREEN, 기존 schema/개인정보·인덱스 및 필터 회귀, 독립 코드검수·QA. 실제 재검증은 사용자 허용 범위 내 진행하고 원본은 메모리 외 보존하지 않는다. 실패 원인을 확인했어도 실제 저장 성공 미검증이면 별도 표시. UI 변경 시 기존 창/프레임/포커스 보호·소유창 정리. 완료 후 안전한 기록과 PR.
