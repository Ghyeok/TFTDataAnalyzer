# Notion 개발 일지 작성 가이드

이 문서는 [TFT Data Analyzer Notion 페이지](https://app.notion.com/p/3de55d93ee2380d1afb5e3baacc79136)의 개발 일지를 바탕으로 정리한 작성 가이드다. 구성은 `3 Rail Coop` 프로젝트의 Notion 작성 가이드를 따르고, 이 프로젝트의 검증·보안 규칙에 맞게 보완했다. 언제 새 페이지를 만들거나 기존 페이지를 갱신할지는 [AGENTS.md의 작업 완료 후 Notion 갱신](../AGENTS.md#작업-완료-후-notion-갱신)을 따른다. 사용자가 별도로 요청한 형식과 내용이 있으면 그 요청을 우선한다.

## 기본 구성

1. **개발 개요**: 개발 날짜, 개발 목표, 코드 기준(커밋 또는 PR 병합 커밋)을 짧게 적는다.
2. **개발 과정**: 작업을 순서대로 나누어 번호가 있는 제목으로 정리한다.
3. **개발 결과**: 확인한 결과와 수치를 적는다. 아직 검증하지 못한 내용은 미확인 상태로 적는다.
4. **근거**: PR, 코드 스냅샷, 사용법 문서, 관련 Notion 페이지를 연결한다.

Notion에서는 개발 과정의 각 작업을 제목이 있는 토글(`<toggle heading="h3">`)로 구성한다. 내용이 길면 기능이나 검증 단계별로 하위 토글을 사용한다. 여러 작업 사이클을 묶은 페이지는 개발 결과 아래에 `상세 기록`, `구현 판단과 근거`, `검증과 한계`, `다음 확인 사항` 절을 둘 수 있다.

- 개발 날짜는 `YYYY.MM.DD` 형식으로 표시한다. 예: `2026.11.16`. 기간은 `2026.10.16 ~ 2026.11.13`처럼 적는다.
- 번호가 있는 토글 제목을 Notion 마크다운으로 작성할 때는 숫자 뒤의 점을 이스케이프한다. 예: `1\. 첫 번째 작업`. 저장 후 제목이 비어 있지 않은지 확인한다.

## 기존 페이지를 갱신할 때

- 과거 기록과 당시 검증 수치는 지우지 않는다. 작성 이후 상태가 바뀌면 페이지 끝에 날짜가 있는 후속 절을 추가한다. 예: `## 후속 기록 — PR #34 병합 · 2026.11.16`.
- 본문의 상태 문구가 현재와 달라 오해를 부를 때만 최소한으로 고친다. 이때 이전 상태였다는 사실이 남도록 쓴다. 예: "Draft PR #34로 기록됐다" → "Draft PR #34로 기록됐고, 2026.11.16 병합됐다".
- 같은 주제의 결과는 기존 페이지에 모으고, 새 페이지가 필요하면 상위 페이지 아래에 다음 번호로 만든다.

## 글을 전개하는 방식

- 구현이 필요한 상황이나 문제를 먼저 설명하고, 선택한 방법과 이유를 적는다.
- 작업 순서에 맞춰 코드 또는 Unity 설정을 소개한 뒤, 주요 함수와 값이 어떤 역할을 하는지 설명한다.
- 코드 블록에는 설명에 필요한 메서드나 클래스의 실제 코드를 넣는다. 앞에 "다음은 `클래스`의 ○○에서 발췌한 실제 코드다."처럼 출처를 밝히고, 일부만 보여줄 때는 `// 중간 코드 생략`처럼 생략된 범위가 오해되지 않게 표시한다.
- 함수, 변수, 클래스, 파일명, 커밋은 인라인 코드로 표시한다. 중요한 역할이나 결정은 굵게 강조한다.
- Unity Editor 창을 다룰 때는 프로젝트 검증 도구로 실제 캡처한 이미지만 사용한다. 합성 테스트나 창 정리 성공을 화면 검증 성공으로 쓰지 않는다.
- 미구현 항목, 테스트하지 못한 내용, 다음 작업이 있다면 현재 상태를 분명히 적는다.

## 문체

- 한국어로 간결하게 설명하고, Riot API·Data Dragon·CommunityDragon·Unity·EditorWindow 등의 기술 용어와 API 이름은 원래 표기를 유지한다.
- 구현한 내용은 "연결했다", 동작 원리는 "호출한다·검사한다"처럼 서술한다.
- 한 문단에는 하나의 흐름이나 개념을 담고, 필요할 때 짧은 목록이나 표로 정리한다.
- 코드의 실행 순서, 입력과 결과, 다른 구성 요소와의 연결 관계를 구체적으로 설명한다.

## 작성 시 확인할 점

- 현재 코드, 작업 사이클의 `Checkpoint.md`, 테스트 결과를 확인해 실제 구현과 글의 내용이 일치하도록 한다.
- 서로 다른 시점과 범위를 구분한다. 예: 수집 요청과 저장 성공, 관련 테스트와 전체 회귀, 로컬 실행과 원격 CI, PR 생성·검수·병합.
- 상태를 완료·진행 중·검수 대기·미검증으로 구분하고, 코드 기준과 검증 시점을 밝힌다.
- 직접 확인하지 않은 테스트 결과나 없는 스크린샷을 만들어내지 않는다. 원인이 확정되지 않은 문제는 원인 후보로 적는다.
- API 키, 플레이어 식별자, 식별 가능한 원본 경기 응답, 개인정보는 기록하지 않는다. 로컬 증거 파일은 경로만 적고 내용을 붙이지 않는다.
- 실행 모델·추론·사용량을 확인할 수 없으면 수치를 만들지 않고 확인 불가로 적는다.
- 기존 일지의 과거 코드가 현재 코드와 다르면 해당 일지의 작성 시점과 현재 상태를 구분한다.
- 저장 후 페이지를 다시 조회해 제목, 토글, 링크, 상위 페이지 연결을 확인한다.

## 간단한 작성 예시

```text
<개발 개요>
- 개발 날짜: YYYY.MM.DD
- 개발 목표: 이번 작업의 목표
- 코드 기준: 병합 커밋 또는 확인한 커밋

<개발 과정>
1. 첫 번째 작업
   작업이 필요한 이유와 선택한 방법
   관련 코드 발췌 (출처와 생략 범위 표시)
   주요 동작과 결과 설명

2. 두 번째 작업
   ...

<개발 결과>
관련 테스트·전체 회귀 결과, 확인한 화면, 남은 미확인 사항

<근거>
PR, 코드 스냅샷, 사용법 문서 링크
```
